# AI 真白花音 TTS 系统设计规格

> 日期：2026-07-30
> 状态：P0/P1/P2/P3/P4 已实现并验收

## 1. 概述

### 1.1 目标

构建一个 **AI 真白花音（ましろ・はな）交互式对话系统**：用户输入文字，系统通过云端 LLM 生成花音风格的回复，再用 GPT-SoVITS 语音克隆技术以花音的音色实时合成语音并播放。

### 1.2 核心需求

| 维度 | 结论 |
|------|------|
| 场景 | 交互式对话——AI 花音能聊天，流式语音回复 |
| 训练环境 | 两张 RTX 3090（各 24GB，现已可用）— 训练花音音色模型 |
| 推理环境 | 笔记本 RTX 4070（8GB）— 实时 TTS 推理 |
| LLM | 云端 API（DeepSeek，OpenAI 兼容接口，流式输出） |
| 输入方式 | 先文字输入，后迭代加语音输入 |
| 界面 | 先 CLI 命令行验证，再做网页界面 |
| 音频素材 | 从零收集（B 站等来源），需要中日双语 |
| 语言 | 中日双语 |

### 1.3 技术选型

- **TTS 引擎**：GPT-SoVITS——中文语音克隆社区最成熟的方案，内置完整数据管线与训练流程，支持中英日多语种，微调效果优秀
- **LLM**：DeepSeek API——中文最强且极便宜（百万 token 约 ¥1-2），流式输出快，OpenAI 兼容接口

### 1.4 非目标（YAGNI）

- 不做多角色/多音色切换（只做花音）
- 不做唱歌合成（只做说话 TTS）
- 不做实时变声/语音转换
- 不自研 TTS 模型（使用 GPT-SoVITS 现有方案）

## 3. 数据采集与处理管线

### 3.1 数据来源

从 B 站收集花音的音频，优先选说话清晰、背景安静的素材：

| 来源类型 | 质量 | 用途 |
|----------|------|------|
| 电台 / 杂谈 / ASMR | ★★★★★ 纯人声、自然说话 | 对话 TTS 最佳素材 |
| 直播录像（杂谈段） | ★★★★ 有时有 BGM | 补充语料 |
| 翻唱 | ★★★ 有伴奏需分离 | 日语素材 + 唱歌风格 |
| 游戏解说 | ★★★ 有游戏音效 | 补充自然语调 |

目标量：中日双语各 15-30 分钟干净人声（越多越好，上限几小时）。

### 3.2 处理管线（6 步）

```
B站视频
  │
  ▼ ① 采集下载         [自定义脚本] BBDown 批量下载
  │   → 视频/音频文件
  ▼ ② 格式标准化       [ffmpeg] 转 48kHz 单声道 WAV
  │
  ▼ ③ 人声分离         [GPT-SoVITS WebUI 内置 UVR5]
  │   → 去掉 BGM/伴奏，只留花音人声
  ▼ ④ 音频切分         [GPT-SoVITS WebUI 内置 VAD]
  │   → 按 silence 切成 5-15s 短句
  ▼ ⑤ 自动标注         [GPT-SoVITS WebUI 内置 Whisper]
  │   → 每段音频自动转写文字，自动识别中/日
  ▼ ⑥ 人工校验         [手动]
      → 修正错字、删低质量片段、确认语种标签
      → 产出 GPT-SoVITS 训练格式
```

### 3.3 自定义代码范围

| 部分 | 是否自定义 | 说明 |
|------|-----------|------|
| ① B站下载脚本 | 自定义 | 用 BBDown 批量下载指定视频/直播录像 |
| ② 格式转换 | 半自动 | ffmpeg 命令行脚本 |
| ③④⑤ 分离/切分/标注 | 用 WebUI | GPT-SoVITS 自带，点按钮即可 |
| ⑥ 人工校验 | 手动 | 听一遍、改错字，最花时间但最关键 |

### 3.4 训练数据输出格式

```
dataset/
├── audio/
│   ├── 001_zh.wav
│   ├── 002_jp.wav
│   └── ...
└── annotation.list
```

`annotation.list` 每行格式：
```
audio/001_zh.wav|花音|ZH|大家好，我是真白花音。
audio/002_jp.wav|花音|JP|こんにちは、花音です。
```

Whisper 自动识别每段是中文还是日文并打标签，校验时确认标签正确。

## 4. 推理管线（对话核心）

### 4.1 流水线并行——"实时"的实现

LLM 边生成文字、TTS 边合成语音、喇叭边播放，三件事并行流水推进：

```
时间轴 →

LLM:    [生成第1句 ████] [生成第2句 ████] [生成第3句 ████] ...
TTS:                [合成第1句 ███] [合成第2句 ███] [合成第3句...] ...
播放:                     [▶ 第1句 ████████] [▶ 第2句 ██████] ...
                          ↑
                    用户听到第一个字 ~0.5-1.5s
```

### 4.2 数据流（单轮对话）

```
用户输入文字
    │
    ▼ conversation.py → 拼接对话历史 + 人设 prompt
    ▼ llm_client.py   → 调 DeepSeek API (stream=True)
    │  流式返回 token
    ▼ sentence_streamer → 攒到句号/感叹号，输出完整句
    │                    （继续攒下一句...）
    ▼ tts_client.py   → POST 本地 GPT-SoVITS API → 返回音频流
    ▼ audio_player.py → 边收音频块边播放
```

### 4.3 关键设计决策

**句子切分策略：**
切分点为 `。！？!?；;\n…`，以及逗号 `，`（当句子超过 ~25 字时强制切）。保证短句快速送 TTS（首音延迟低），长句不会等太久才出声。

**并发模型——asyncio + 队列：**
```
LLM流 ──► sentence_queue ──► TTS合成 ──► audio_queue ──► 播放
(生产文字)    (缓冲)        (生产音频)     (缓冲)       (消费)
```
每个阶段是独立的 asyncio Task，用 `asyncio.Queue` 连接。各阶段独立运转、互不阻塞，天然背压控制，每个阶段可独立测试。

**TTS 服务——直接用 GPT-SoVITS 自带 API Server：**
- 启动 GPT-SoVITS 的 `api_v2.py`，加载微调模型，监听本地端口
- `tts_client.py` 是 HTTP 客户端，调用 `POST /tts`
- 不修改 GPT-SoVITS 源码——升级可无缝跟进
- `tts_client.py` 封装为统一接口，后续如需换引擎只改此文件

**音频播放：**
用 `sounddevice` 库流式播放（收到音频块即写入声卡），连续播放队列保证多句音频无缝衔接。

**对话历史管理：**
保留最近 N 轮对话（如 10 轮）控制 token 用量与成本。花音人设 system prompt 始终在最前面。超出时自动丢弃最早的非系统消息。

**花音人设（persona.py）：**
通过 system prompt 定义花音的性格、说话风格、口头禅、语癖、中日双语切换习惯。实现时根据花音实际人设定制打磨。

### 4.5 错误处理

| 场景 | 处理 |
|------|------|
| DeepSeek API 超时/报错 | 重试 1 次，失败则提示"花音走神了…" |
| GPT-SoVITS 服务未启动 | 启动时检测，明确报错"TTS 服务未运行，请先启动" |
| LLM 返回空内容 | 跳过该轮，提示重试 |
| TTS 合成某句失败 | 跳过该句语音，文字照常显示 |

## 5. 训练管线

### 5.1 训练步骤（GPT-SoVITS WebUI 内置）

```
annotation.list
    │
    ▼ 0d 语义文本标注     [WebUI 内置] 提取文本语义特征
    ▼ 1A 数据格式化       [WebUI 内置] 转换为训练张量
    ▼ 1B 微调 SoVITS 模型  [WebUI 内置] 训练声音合成模型
    ▼ 1C 微调 GPT 模型     [WebUI 内置] 训练韵律/语调模型
    │
    ▼ 产出模型文件 (ckpt)
```

### 5.2 3090 训练配置建议

| 参数 | 建议值 | 说明 |
|------|--------|------|
| batch_size | 6-12 | 24GB 显存充裕，可以开大 |
| GPU 数 | 2 | GPT-SoVITS 支持多卡训练 |
| 训练时长 | ~30min-2h | 取决于数据量，语音克隆不需要太久 |

### 5.3 模型部署

训练完成后，将 ckpt 模型文件拷贝到 4070 笔记本，GPT-SoVITS API Server 加载微调模型对外提供 TTS 服务。

整个训练环节自定义代码量接近零——全部是 WebUI 操作。

## 6. 交付阶段

### 6.1 阶段总览

```
P0 验证 ──→ P2 CLI 对话 ──→ P1 训练(提升音质) ──→ P3 Web界面 ──→ P4 语音输入
  半天         2-3天              1-2天               2-3天          1-2天
```

P1 训练可以和 P2 并行——P0 用零样本先把 CLI 做出来，同时用 3090 训练高质量模型，模型好了替换进去。

### 6.2 P0：最小验证

目标：半天内听到花音的声音，证明整条链路通。

1. 4070 上安装 GPT-SoVITS
2. 从 B 站下载一段花音的清晰语音（10-30s）
3. 写一个约 50 行的脚本：用户输入文字 → DeepSeek 生成回复 → GPT-SoVITS 零样本合成 → 播放
4. 听效果，确认方向正确

P0 不需要训练、不需要数据管线、不需要流式，是端到端验证脚本。

### 6.3 P3：Web 界面

```
浏览器 (HTML/JS)
    ↕ SSE（流式传输文字 + 音频）
FastAPI 后端
    └─ 复用 dialogue/ 对话核心（不改逻辑，只加一层 API 封装）
```

当前实现为 frontend/web.py + frontend/web.html：文字和 WAV 音频通过
POST /api/chat 的 SSE 事件流传输；相比 WebSocket，SSE 足够覆盖单向 LLM/TTS
流式回复，并保留 HTTP 部署、代理和断线重连的简单性。后续可在此基础上增加
音频可视化。

### 6.4 P4：语音输入

| 方案 | 说明 |
|------|------|
| 本地 Whisper | 在 4070 上跑 faster-whisper，零成本，中日语都支持 |
| 云端 ASR | 如阿里语音识别 API，更准但收费 |

frontend/web.html 通过 MediaRecorder 采集 WebM/Opus，POST /api/transcribe 使用
faster-whisper 转写后自动复用同一条文字对话链路。上传限制默认为 15 MiB，模型未安装
时接口返回 503，页面禁用录音按钮。

验收记录：faster-whisper large-v3 在 GPU 0 上成功转写项目生成 WAV，返回 zh 和
language_probability=1.0。

## 7. 测试策略

- **对话核心各模块单元测试**：句子切分器、LLM 客户端（mock API）、TTS 客户端（mock API）、对话历史管理
- **流水线集成测试**：mock LLM 和 TTS，验证 asyncio 队列协调正确、音频按序播放
- **端到端验证**：P0 脚本本身就是端到端验证
- **TTS 客户端接口测试**：统一接口可 mock，便于后续换引擎时回归测试
